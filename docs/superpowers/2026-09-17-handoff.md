## The two decisions the user took, which the code must keep

1. **Judging is unobtrusive.** It lives behind Settings — not a section on the
   home screen, not a tab, and with no count badge anywhere. Their words:
   *"rather buried somewhere in the settings. this is a mechanic i actually
   want to work towards removing the human in the loop."* Do not surface
   pending-work counts on home or in the bottom bar.
2. **The pair card keeps all five answers** the web offers — Keep A, Keep B,
   Write one, Discard both, Dismiss — rather than being reduced for the phone.

Carried from Part E, also the user's:

3. **No background prefetch.** Nothing is fetched that nobody asked for. An
   unreachable server is said plainly (`Server unreachable`, with when the
   content was fetched and a retry) over whatever was held, or over nothing.
   The real answer to being offline is a later self-contained app — an engram
   on the device replacing the server *by default* — and `Reader` is the seam
   it plugs into. Nothing above `core` may name an implementation.

## Things worth knowing before touching anything

- **The search divider is drawn from `past_cliff`, not `weak`.** The programme
  document says `weak` for both; `_results.html` has always used `past_cliff`
  for the rule and `weak` for the loose badge. `docs/api.md` states it
  correctly. `railOf` in `android/app/.../ui/Rail.kt` implements it.
- **`GET /artifacts/{id}` records an open, including on a revalidation.** The
  app must fetch artifact detail only when a person opens one, never from a
  background refresh. `ArtifactScreen` is the only caller.
- **The API fixtures are not written by hand.**
  `src/web/android_fixtures.rs` builds a small base, calls the real routes and
  writes `android/core/src/test/resources/api/*.json` under
  `ENGRAM_WRITE_ANDROID_FIXTURES=1`; on every ordinary run it asserts the
  committed files still have the shape a fresh answer has. A field renamed on
  the server fails a Rust test that names the Android file. If a shape changes
  on purpose: regenerate, then run the Android tests.
- **Do not assert fixture counts in Kotlin.** Two tests did and broke the
  moment the fixture base grew (`26c4be7`). Assert the property.
- **Room migrations are hand-written, not destructive.** Version 1 holds the
  outbox, which is the one thing on the device that exists nowhere else.
  `MigrationTest` builds a v1 file from `1.json`'s SQL and opens it through
  `Db.open`, so Room validates the migration. It was shown to fail on a
  deliberate typo.
- **`android/.gitignore` excepts `core/schemas/*.db.*/`** — the repository's
  `*.db.*` rule matched Room's schema directory by accident, because the
  database class is `…core.db.Db`.

## Running things

```sh
cargo test                                   # whole tree; 2873 passing in lib
cargo clippy --all-targets -- -D warnings    # clean
cd android && ./gradlew lintDebug testDebugUnitTest :app:assembleDebug
```

Two Android entry points that are off by default:

- `-Pengram.pictures=1` makes `PicturesTest` write PNGs of the screens' parts
  to `app/build/pictures/`. Worth doing and *looking at* — it found a real
  layout defect in Part E while no phone was in the loop.
- `-Pengram.live.origin=… -Pengram.live.token=…` points `LiveServerTest` at a
  running engram. It skips itself when they are absent (the 4 skipped tests).

### A throwaway server to run against

The scratch instance this session used has been torn down. To rebuild one —
its own database, its own Qdrant, its own port, nothing of the user's touched:

```sh
S=<a scratch dir>; mkdir -p $S
podman run --rm -d --name engram-e2e-qdrant -p 127.0.0.1:16333:6333 \
  docker.io/qdrant/qdrant:v1.18.2
./target/debug/engram --hash-password scratch-e2e     # for auth.local.password_hash
# config.toml: bind 127.0.0.1:18080, store.path under $S, vector.url
#   http://127.0.0.1:16333, collection engram_e2e_scratch, infer.tiers.{efficient,deep}
#   and infer.embed pointed at http://127.0.0.1:9/v1 (nothing answers; that is
#   the point — it exercises the failure paths), auth.mode "local".
./target/debug/engram --config $S/config.toml
```

Then pair as a phone does: POST the login form to `/auth/login` with a cookie
jar, POST `/ui/app/grant` to draw a code, unescape the `engram://pair?…` URI
out of the HTML (it is HTML-escaped — `&#38;`), and POST `{code, device}` to
`/api/v1/pair/claim` for a device token.

## What has never run

**Nothing has been run on a phone or an emulator.** That is deliberate and the
user's instruction: the device pass happens once the app is feature-complete,
and work is not to be gated on it. Do not propose holding a release for it.
Say the risk once if it is relevant, then carry on.

Also unrun: the browser extension (no test suite; `panel.js` was changed by
reading it and syntax-checked with `node --check`), and the Android 10–13
fallbacks added for `minSdk` 29 — the CI emulator is API 35.
