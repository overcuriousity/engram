# Judging: the API's second slice, and the app's (Parts B-2 and F) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The decisions a person makes about the base — duplicate pairs, gaps,
what the base did while they were away — cross `/api/v1` and are answerable
from the phone, with every one of them undoable.

**Architecture:** The routes obey the read contract already in `docs/api.md`
without adding to it: lists are `{items, next}`, reads carry an `ETag`, writes
answer a status and `{error}`. Each write shares the core call its HTML sibling
already uses, extracted where the handler holds it. On the phone the surfaces
sit behind Settings, the pair review is one card at a time, and every write
goes through the outbox like every other write the device owes.

**Tech Stack:** Rust, axum 0.8; Kotlin, Compose, Room, as Part E left them. No
new dependency on either side.

**Spec:** `docs/superpowers/specs/2026-09-08-android-companion-design.md`,
Parts B and F. The contract is `docs/api.md`; this slice adds routes to it and
changes none of its rules.

## Decisions taken with the user (2026-09-17)

- **Judging is unobtrusive.** It lives behind Settings — not a section on home,
  not a tab, and with no count badge anywhere. In the user's words: *"this is a
  mechanic i actually want to work towards removing the human in the loop."* A
  queue of chores on the screen the app opens on is an interface asking to be
  served, and this part is meant to shrink.
- **The pair card keeps all five answers** the web offers: Keep A, Keep B,
  Write one, Discard both, Dismiss. Not reduced for the phone.
- Carried from Part E and unchanged: nothing is fetched that was not asked for;
  an unreachable server is said plainly; `Reader` is the seam.

Not crossing, by the programme and by instruction: applying a tuning
recommendation (it writes `config.toml`), instance configuration,
`--grant-judge`, API token management, the extension offer.

## What the shapes must say, and why

Three additions to the vocabulary `docs/api.md` already fixes. They follow rule
3 — facts, not renderings — and that has one consequence worth stating up
front, because it is the decision this slice is easiest to get wrong:

**A set-aside row carries its `kind`, not its buttons.** The web builds a list
of `{href, label}` per row; that is a rendering, and an API that sent it would
be telling the client where to tap. The row sends `kind` — one of `merged`,
`generated`, `hidden`, `buried`, `parked`, `unverified` — together with the
ids an action would need (`artifact_id`, and `corpus_id` or `merge_id` where
the kind has one). Which answers a kind admits is the client's to know, and
both clients already know it because each answer is a route of its own. A kind
this app has never heard of renders with no buttons rather than crashing,
which is what lets the server grow a seventh.

**A pair says who has looked at it.** `unjudged` means the sweep put it there
on a cosine score and nothing has read it since, so a client must not print
"these two cover the same ground" over it — that is a finding, and on a pending
row it is a claim made by nobody. `via_link` means no cosine was ever computed,
so `percent` must not be shown as a measured similarity. `mergeable` says
whether *Write one* would be refused by the merge path, so a client can leave
the button out rather than offer a press that can only come back a validation
error. These three are the same honesty the search divider is: the card is
allowed to say only what somebody actually established.

**A gap is a question, not an error.** Gaps list clustered, each cluster with
its label, how it was labelled (`model` or `terms`), and its members. A member
carries its `kind` and `id` because that is what dismissing one names.

## Global Constraints

- The read contract in `docs/api.md` is not changed, only extended.
- Every write route shares the core call its `/ui/ops` sibling uses; where the
  sibling holds the logic in its handler, the logic is extracted and both call
  it. Existing `ops.rs`, `insights.rs` and `ui.rs` tests stay green unchanged.
- `Transport` stays `internal` to `core`; screens reach the server through
  `Reader`, `Ask` and `Outbox` only.
- No judging surface on the app's home screen or bottom bar, and no badge.
- No test on the phone asserts anything about ranking or ordering.
- UI copy is minimal: a term and a short gloss, never an explanatory sentence.
- Targeted tests before each commit; a full `cargo test` and a full
  `./gradlew lintDebug testDebugUnitTest :app:assembleDebug` at the end.
  Evidence of what ran goes in each commit message.
- Commits end with `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`.

### Task 7: The screens

**Files:** create `app/.../ui/JudgeScreens.kt`; modify `SettingsScreen.kt`, `Nav.kt`.

- **The entry.** Settings gains a section — *Judging* — with three lines:
  *Duplicate pairs*, *Gaps*, *While you were away*. Counts appear on those
  lines once opened, never on home and never as a badge.
- **The pair review.** One card at a time, `n of m` above it. Both sides with
  their label and excerpt, the finding between them, and the five answers:
  *Keep "<a>"*, *Keep "<b>"*, *Write one*, *Discard both*, *Dismiss*. *Write
  one* is absent where `mergeable` is false. A confirmation names what is being
  hidden, as the web's does. An answer enqueues and advances to the next card;
  an *Undo* stays on screen until the next answer, and takes the row back out
  of the outbox while it is still queued.
- **Gaps.** The clusters, each with its members; a member can be dismissed;
  *Forget all* behind a confirmation.
- **While you were away.** The set-aside rows, newest first: label, why, what
  is beside it, the caveat, and the actions its `kind` admits. An unknown kind
  renders with none.
