# Taxonomy Rename Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rename the domain so the code says what the system does: a **corpus** is pasted, split into **segments**, which are synthesised into **artifacts**.

**Architecture:** One vocabulary, applied at every layer — SQLite schema, Rust modules and types, the Qdrant payload, the HTTP and UI routes, the templates, and the docs. Migration `0007` renames tables, columns and enum values in place; `--reindex` gains a payload key mapping so an existing collection converts without re-embedding.

**Tech Stack:** Rust 2024, sqlx/SQLite, Qdrant REST, askama templates.

## Global Constraints

- Rust edition 2024, `rust-version = "1.94"`.
- `cargo test` and `cargo fmt --check` pass before every commit. (`cargo clippy` is unavailable on this machine; CI is the gate.)
- No behaviour changes. This is a rename plus one stage-name correction. If a step tempts you to fix logic, stop and leave it.
- Existing data must survive: the operator has a populated `engram.db` and a live Qdrant collection.
- Comments explain *why* and match the surrounding voice.

## The vocabulary

| Old | New | What it is |
|---|---|---|
| source | **corpus** | The pasted text, hashed for dedup. The data source. |
| window | **segment** | A line range of the corpus sized to fit the model's context. Mechanical, not semantic. Also the retry memory. |
| chunk | **artifact** | The synthesised, standalone piece that gets embedded, searched and read. |
| `Stage::Segment` | `Stage::Synthesize` | The stage that calls the model. Segmenting is the free local split; synthesis is the inference. |
| `SourceStatus::Segmenting` | `CorpusStatus::Synthesizing` | Same correction, in the status enum. |

Relations, unchanged: an artifact references one segment (`segment_idx`) and a line range of its corpus (`corpus_span`); a segment references its corpus.

- [ ] **Step 1: Write the migration**

`migrations/0007_taxonomy.sql`. SQLite supports `ALTER TABLE … RENAME`, and renames carry indexes and foreign keys with them.

```sql
-- The domain now says what it does: a corpus is pasted, split into segments,
-- and those are synthesised into artifacts. The old names described the
-- mechanism (a "chunk" of text) rather than the thing the reader searches for.
ALTER TABLE sources RENAME TO corpora;
ALTER TABLE chunks  RENAME TO artifacts;
ALTER TABLE segment_windows RENAME TO segments;

ALTER TABLE artifacts RENAME COLUMN source_id   TO corpus_id;
ALTER TABLE artifacts RENAME COLUMN source_span TO corpus_span;
ALTER TABLE artifacts RENAME COLUMN window_idx  TO segment_idx;
ALTER TABLE segments  RENAME COLUMN source_id   TO corpus_id;

-- The stage that calls the model is synthesis. Splitting a corpus into
-- segments is the free local step and never had a stage of its own.
UPDATE jobs SET stage = 'synthesize' WHERE stage = 'segment';
UPDATE jobs SET target_kind = 'corpus'   WHERE target_kind = 'source';
UPDATE jobs SET target_kind = 'artifact' WHERE target_kind = 'chunk';
UPDATE corpora SET status = 'synthesizing' WHERE status = 'segmenting';
```

Note for the implementer: read `migrations/0002_fts.sql` first. The FTS5 table and its triggers reference `chunks` by name; a rename does **not** rewrite trigger bodies. Drop and recreate them in this migration against `artifacts`, keeping their current column list (`text`, `title`, `tags`) and their current scoping.

### Task 3: Vector payload and the reindex migration

**Files:**
- Modify: `src/vector/mod.rs`, `src/vector/qdrant.rs`, `src/vector/memory.rs`, `tests/integration_qdrant.rs`

**Interfaces:**
- Produces: `VectorPayload { artifact_id, corpus_id, .. }`; `reindex` rewrites old payload keys as it copies.

- [ ] **Step 1: Rename the payload fields**

`VectorPayload::chunk_id` → `artifact_id`, `source_id` → `corpus_id`. These are serde field names, so the wire format follows automatically. Then fix the four hard-coded key strings: the payload index at `src/vector/qdrant.rs:423` and the filter at `:1049`, plus their counterparts.

- [ ] **Step 2: Make `--reindex` the migration path**

The copy loop at `src/vector/qdrant.rs:660` passes `p.payload` through untouched, so a collection written under the old names would keep them. Map the keys as they are copied:

```rust
                // A generation written before the taxonomy rename carries the
                // old payload keys. Renaming them here is what makes
                // `--reindex` the migration: the vectors are already correct,
                // and re-embedding to change two key names would be absurd.
                let mut payload = p.payload.clone();
                if let Some(obj) = payload.as_object_mut() {
                    if let Some(v) = obj.remove("chunk_id") {
                        obj.entry("artifact_id").or_insert(v);
                    }
                    if let Some(v) = obj.remove("source_id") {
                        obj.entry("corpus_id").or_insert(v);
                    }
                }
```

and use `payload` in the `batch.push`.

- [ ] **Step 3: Test it**

Add to `tests/integration_qdrant.rs`, following the existing style there:

```rust
#[tokio::test]
#[ignore]
async fn reindex_renames_pre_taxonomy_payload_keys() {
    // A collection written before the rename. Built through raw REST, because
    // engram itself will no longer produce these keys.
    let name = "engram_it_taxonomy";
    let v = fresh(name, 4).await;
    raw(
        reqwest::Method::PUT,
        &format!("/collections/{name}_v1/points?wait=true"),
        Some(serde_json::json!({
            "points": [{
                "id": "00000000-0000-0000-0000-000000000001",
                "vector": { "dense": [1.0, 0.0, 0.0, 0.0] },
                "payload": {
                    "chunk_id": "c1", "source_id": "s1", "text": "t",
                    "tags": [], "created_at": 1
                }
            }]
        })),
    )
    .await;

    v.reindex(4, false).await.unwrap();

    let hits = v
        .search(&[1.0, 0.0, 0.0, 0.0], &Default::default(), 1, &SearchFilter::default())
        .await
        .unwrap();
    assert_eq!(hits[0].payload.artifact_id, "c1");
    assert_eq!(hits[0].payload.corpus_id, "s1");
}
```

Note for the implementer: read the existing helpers in that file first — `fresh`, `raw`, `cfg` — and match how they name generations. The point of the test is the key mapping, so adjust the scaffolding freely to make it run, but do not weaken that assertion.

Run: `cargo test --test integration_qdrant -- --ignored`
Expected: all pass, against the running Qdrant.
